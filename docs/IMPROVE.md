# Improve the harness

Run this at Deploy, after the review fixes and before the merge. It changes only the harness. If review findings are still open, or the review says it left part of the change unread, say so first and leave them to the review fixes.

1. Look at what went wrong on this change: the review's findings, what the person corrected and what the checks caught. Look in:
   - the review's report, including what it says it didn't read, and the review sections of docs/STATUS.md
   - the person's own messages in the coding agent's session logs, for anything they had to correct or say more than once. Claude Code keeps one `.jsonl` file per session in `~/.claude/projects/`, in a folder named after the path the session ran in, so a change's sessions can be in the main checkout's folder and its worktree's. Each entry has a `gitBranch`, which finds this change's sessions, but a folder for another copy of the repo can hold a branch with the same name, so go by the path too. The folder names start with `-`, which jq and grep read as an option, so pass them as `./-Users-...`. Teammate messages and task notifications arrive as user messages too, so leave them out, or they bury the person's own
   - the hook results and failed checks in those logs, and anything the agent says it got wrong. Each run of the Stop hook is an entry with `subtype` `stop_hook_summary`, and a failure is in its `hookErrors`. A tool call that a hook or a permission check stopped is in the call's result, with `is_error` set, so look there for what was stopped and what the agent did instead, the subagents' logs included. Those are in the session's `subagents/` folder, with each one's type in its `.meta.json`. Group the text of every failed tool result across all the folders, too: that finds shell errors nobody mentioned, such as the zsh ones `AGENTS.md` now warns about
   - the agents' shell commands in those logs, for what the person never saw: servers started in the background, and anything run on `data/accountable.db` or the working tree
   - the harness changes on the branches not merged yet, with `git log main..<branch> -- AGENTS.md docs/IMPROVE.md docs/REVIEW.md scripts .claude .mcp.json` for each branch `git branch` lists, so this run doesn't make a fix another branch already has. Say in docs/STATUS.md what the merge will need to keep from both. Search those branches' sessions as well, because branches built side by side make the same mistake at the same time
2. For a mistake that has happened twice, in this change or across changes, add the correction to AGENTS.md or docs/REVIEW.md, or suggest a change to docs/STANDARDS.md for the person to make. If a tool can catch it, add it to the checks instead. Check Seen once below for earlier times, then search the earlier changes' sessions for the same commands or words: a habit nobody noticed, such as stopping the app with `pkill`, never reached Seen once. Count two mistakes with the same cause as one seen twice. If the person keeps saying something AGENTS.md already says, check whether an agent broke the rule before adding anything. A mistake that a hook or Claude Code already stops, such as a bare `python3` or a chain of `sleep`s, needs nothing more unless it did harm before it was stopped.
3. Add each mistake that has happened only once to Seen once, with the change it came from and the fix you'd make if it comes back. Take out any that became a rule.
4. Remove anything out of date, in the harness docs and in docs/STATUS.md, such as a finding still marked open after it was fixed.
5. Say in docs/STATUS.md what this run changed.
6. Improve this file, so that the next round makes a better change. Keep this as the last step.

When you count a mistake in the logs, search the tool results and the person's messages, not whole entries, and leave out the session doing this run. Its own searches hold the words they look for, so a search of the whole file counts them. A subagent's log shows what it read: a report that says it checked something it never opened, or an output saved to a file that it never opened, is a gap in that report.

## Seen once

- **dark-mode, wrong baseline:** the plan said to compare light mode with `main`, but the local `main` has no app. The build used the commit the branch started from. Fix if it comes back: plans name the branch's starting commit, from `git merge-base`, as the baseline.
- **dark-mode, test data clash:** two end-to-end tests on the same worker added a deal with the same name, and one found the other's. Fix if it comes back: each test names its records after itself.
- **multi-user, `python` in a comment:** `cli.py` said to run it with `python -m`, though the project runs Python through uv, and the owner had to point it out. Fix if it comes back: a check that fails on any `python` or `pip` command in the repo that doesn't start with `uv run`.
- **multi-user, slow on a remote database:** on the first walk on Supabase, each screen took about 5 seconds. Every API call made 8 to 16 round trips one after another, and `render.yaml` put Render across the Atlantic from the database. `test_limits.py` now caps the queries per call. Fix if it comes back: a plan that moves the data across a network counts the round trips each screen costs, and puts the server in the database's region.
- **multi-user, a check the client controls:** the local copy decided a request came from this computer by its Host header, which the sender sets, so anyone who could reach it could sign in (review, Important). Fix if it comes back: REVIEW.md's Security pass asks, for every check on who sent a request or where from, whether the sender can set what it reads.
- **multi-user, the Stop hook during a team build:** the lead's Stop hook ran `npm run check:quick` 104 times while the teammates worked, about 81 minutes in all, and 21 runs failed on teammates' unfinished files that the lead didn't own. Fix if it comes back: the hook skips the lead's turns while a team is working, and the lead runs `npm run check:quick` at the end of each phase.
- **multi-user, a fixable bug called a library's way:** the search box told screen readers its list was open while it was closed. The owner was told that's how cmdk works and accepted it as a nit. A later session fixed it in a few lines. Fix if it comes back: before calling a bug how a library works, try to fix it, and say what the fix would take.
- **company-settings, a message that looked like a box to type in:** the spec's screen gave the ask for a company name the page color and the inputs' rounding, and ui-check passed it because the spec asked for it. The build agent saw that it looked like an empty box, and the owner had it changed to text after an icon. Fix if it comes back: ui-check asks of anything that takes no input whether it could be taken for a box or a button, whatever the spec says.
- **bills, the form and the API differ on a default:** the Add form fills in the due date as 30 days after the bill date with date-fns, while the API stops at the calendar's last day. So for a bill dated in the last 30 days of 9999, the form would send a date the API refuses (review, nit). Fix if it comes back: a rule the backend and the form both apply gets shared cases that both sides' tests read, as `shared/totals-cases.json` does for the sums.
- **quotes, a number in the body font:** the deal and organization Quotes panels showed each quote's number in Instrument Sans, because the shared `LinkedList` set every name in it, where every other number is in JetBrains Mono. ui-check caught it. Fix if it comes back: `quality.spec.ts` checks on every page that text shaped like an id, an amount or a date is in JetBrains Mono.
- **quotes, a dark scrollbar on the white sheet:** the preview keeps the paper colors in dark mode, but its scroll area took the page's dark scrollbar. ui-check caught it. Fix if it comes back: `visual-design.md` says that an area keeping the paper colors in dark mode sets its own scrollbar colors too, and ui-check looks at the scrollbars of every such area.

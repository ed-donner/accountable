# Improve the harness

Run this at Deploy, after the review fixes and before the merge. It changes only the harness. If review findings are still open, say so first and leave them to the review fixes.

1. Look at what went wrong on this change: the review's findings, what the person corrected and what the checks caught. Look in:
   - the review's report and the review sections of docs/STATUS.md
   - the person's own messages in the coding agent's session logs, for anything they had to correct or say more than once. Claude Code keeps one `.jsonl` file per session in `~/.claude/projects/`, in the folder named after this project's path. Each entry has a `gitBranch`, which finds this change's sessions. Teammate messages and task notifications arrive as user messages too, so leave them out, or they bury the person's own
   - the hook results and failed checks in those logs, and anything the agent says it got wrong. Each run of the Stop hook is an entry with `subtype` `stop_hook_summary`, and a failure is in its `hookErrors`. A tool call that a hook or a permission check stopped is in the call's result, with `is_error` set, so look there for what was stopped and what the agent did instead, the subagents' logs included
   - the agents' shell commands in those logs, for what the person never saw: servers started in the background, and anything run on `data/accountable.db` or the working tree
   - the harness changes on the branches not merged yet, with `git log main..<branch> -- AGENTS.md docs/IMPROVE.md docs/REVIEW.md scripts .claude` for each branch `git branch` lists, so this run doesn't make a fix another branch already has. Say in docs/STATUS.md what the merge will need to keep from both
2. For a mistake that has happened twice, in this change or across changes, add the correction to AGENTS.md or docs/REVIEW.md, or suggest a change to docs/STANDARDS.md for the person to make. If a tool can catch it, add it to the checks instead. Check Seen once below for earlier times, and count two mistakes with the same cause as one seen twice. If the person keeps saying something AGENTS.md already says, check whether an agent broke the rule before adding anything.
3. Add each mistake that has happened only once to Seen once, with the change it came from and the fix you'd make if it comes back. Take out any that became a rule.
4. Remove anything out of date, in the harness docs and in docs/STATUS.md, such as a finding still marked open after it was fixed.
5. Say in docs/STATUS.md what this run changed.
6. Improve this file, so that the next round makes a better change. Keep this as the last step.

## Seen once

- **dark-mode, wrong baseline:** the plan said to compare light mode with `main`, but the local `main` has no app. The build used the commit the branch started from. Fix if it comes back: plans name the branch's starting commit, from `git merge-base`, as the baseline.
- **dark-mode, test data clash:** two end-to-end tests on the same worker added a deal with the same name, and one found the other's. Fix if it comes back: each test names its records after itself.
- **multi-user, `python` in a comment:** `cli.py` said to run it with `python -m`, though the project runs Python through uv, and the owner had to point it out. Fix if it comes back: a check that fails on any `python` or `pip` command in the repo that doesn't start with `uv run`.
- **multi-user, slow on a remote database:** on the first walk on Supabase, each screen took about 5 seconds. Every API call made 8 to 16 round trips one after another, and `render.yaml` put Render across the Atlantic from the database. `test_limits.py` now caps the queries per call. Fix if it comes back: a plan that moves the data across a network counts the round trips each screen costs, and puts the server in the database's region.
- **multi-user, a check the client controls:** the local copy decided a request came from this computer by its Host header, which the sender sets, so anyone who could reach it could sign in (review, Important). Fix if it comes back: REVIEW.md's Security pass asks, for every check on who sent a request or where from, whether the sender can set what it reads.
- **multi-user, the Stop hook during a team build:** the lead's Stop hook ran `npm run check:quick` 104 times while the teammates worked, about 81 minutes in all, and 21 runs failed on teammates' unfinished files that the lead didn't own. Fix if it comes back: the hook skips the lead's turns while a team is working, and the lead runs `npm run check:quick` at the end of each phase.
- **multi-user, a fixable bug called a library's way:** the search box told screen readers its list was open while it was closed. The owner was told that's how cmdk works and accepted it as a nit. A later session fixed it in a few lines. Fix if it comes back: before calling a bug how a library works, try to fix it, and say what the fix would take.
- **products, a review cut short:** the reviewer's shell hook stopped two of its commands, and it left the end-to-end tests, the table rewrite and the search move unread, though Read could open them. It said so, and its second pass found the review's one Important finding. The hook now lets `sed -n` through, which most of the stopped commands were. Fix if it comes back: `reviewer.md` says to open a file with Read when the hook stops a command, and never to leave part of the change unread.

# Spec: Frontend

Part of the [spec](../spec.md), which has the summary, the terms, the quality rules and the index of every area file.

## Frontend

- **Data:** TanStack Query holds all server data, and it refetches when the window regains focus, which is also when teammates' changes show up. After any write, invalidate everything. With a small team and this little data, that's simple and hard to get wrong. Queries and saves use `networkMode: 'always'`, because the local copy runs with no internet, and the browser reporting it's offline would otherwise pause them (C2).
- **Signing in:** `lib/session.ts` holds the session and is the one place that signs in and out, for both copies. In the shared app it uses Supabase's JavaScript client with the publishable key, which keeps the session in this browser's storage and renews the token before it expires. In the local copy, the sign-in screen asks the backend's local sign-in route for a token, through `lib/api.ts`, and `session.ts` keeps it in storage, where each request reads it. If storage is off or full, `session.ts` keeps the token itself, so the person stays signed in until the page is reloaded. `session.ts` imports nothing from `api.ts`, so the two load in one order. The frontend knows which copy it's in from whether the Supabase URL and key were built in (W2): `npm start` and Render build them in, and `npm run dev` never passes them to Vite (C9). `lib/api.ts` adds the token to every request. A 401 shows the sign-in screen with U6's message, but only if the session the request went out in is still going: each sign-in begins a session with a new id, so a refusal arriving after someone has signed out and in again leaves the new session alone. `SignedIn` gives each session its own query cache, made when the session begins and dropped when it ends, and the sign-in screen has one too. So nothing from one session shows in the next, even a reply or a pipeline move that finishes after it ended, which lands in the old cache (U5). Messages go the same way. Sonner keeps them for the whole page, and hands those still showing to the next session's `Toaster`, so `SignedIn` takes them away when a session ends, before the next one's `Toaster` starts. And every message goes through `useNotify` in `lib/notify.ts`, which shows it only if the session the component began in is still going, so a save whose reply comes after sign-out says nothing.
- **Today:** the page can stay open for days, so anything on screen that depends on the date uses `useToday`, which checks the clock every minute and whenever the window is used again. The dashboard reads its figures again when the day changes, and so does its Money section. Which bills are overdue, in the Bills table, the filter's counts, a bill's page and an organization's Bills panel, is worked out in the browser from each bill's due date and `useToday`, so a bill turns overdue at midnight without a fresh read (E8). The browser's today is the device's, and the team shares one time zone, so it matches the backend's.
- **Instant updates:** only the pipeline move and the follow-up tick update the screen before the server replies, and both roll back on failure. Moves share one mutation scope and ticks another, so each kind is sent one at a time and in order. Reads they would affect are cancelled first, so an older reply can't overwrite them. The board shows what the server has confirmed plus the moves still on their way, so a failed move or tick puts back only its own change.
- **Money:** `lib/money.ts` shows a deal's whole dollars as `$48,000` and a product's cents as `$49.50` or `$1,250.00`, always with two figures after the point (G3). It also turns a typed price into cents (G4) by reading the dollars and the cents as two whole numbers, never by multiplying a decimal by 100, which gives 28.999999999999996 for 0.29. A price that can't be read, or has a third figure after the point, is refused rather than rounded. The frontend and the backend only ever pass prices to each other as whole cents. A bill's amount and tax are shown and read the same way, and the bill form's total adds the two typed amounts as whole cents, for show only: the backend works out the total it saves and sends (E4). A sum of bills, from the Money route or added up for an organization's Bills panel, is a BigInt, which `price` shows the same way, because it can pass the 2^53 cents a JavaScript number holds exactly (E19, E20). The cash flow's sums and balances arrive the same way, and a balance below zero shows with its minus sign before the currency, as `-$4,250.00`. The opening balance is read like a price, with a minus sign allowed in front, so an overdrawn account can be typed in (B24).
- **Board figures:** worked out in the browser from the deals list, so they change as a card lands. They use the same formula as the backend, with a unit test on each side using the same cases.
- **Dragging:** a 6px move starts a drag, so a click still opens the deal. Keyboard dragging comes from dnd-kit's keyboard sensor, set to pick up and drop on Space only, because by default Enter would pick up the card instead of opening the deal. Cards are memoized to stay smooth at 500 deals. Columns aren't virtualized, because that conflicts with dropping a card anywhere. Each column is a droppable, and the board has one draggable that's pointed at a card as it's picked up. While a card is dragged, the others slide apart around a faint slot showing where it will land, and the gap closes behind it. `@dnd-kit/sortable` isn't used: its per-card hooks re-render every card each time a drag crosses a card, which took 241ms at 500 deals. The longest task on this board is about 70ms to 180ms, slowest on the first drags after loading.
- **Dialogs inside dialogs:** a form in a second dialog, such as adding an organization from a picker, stops its submit event from going further. React passes events up through portals, so it would otherwise submit the form underneath too.
- **Search:** the search box waits for a 150ms pause in typing, then asks `GET /search` through TanStack Query, keyed by the text, so a newer search's reply always wins and going back to an earlier text shows its results at once. The box lives in `components/Search.tsx` and knows nothing about any area's records. Each area gives it its groups, each with its heading, the address a result opens, and how a result's detail shows, such as a deal's stage chip or a product's price. `App.tsx` hands the box the groups in order, CRM first, and hands the box to the shell. The box's label for screen readers and its message for no matches are made from the groups' names, so a later area's group joins them by itself.
- **Company settings:** the page's form uses React Hook Form and Zod, as the record forms do, filled from `GET /settings` and saved with `PATCH /settings` through `useWrite` in `lib/records.ts`, so everything is read again after a save, as after any other. The save's reply goes straight into the settings' query, so who last changed them shows at once. When TanStack Query reads the settings again, such as when the window is used again, the form takes the new values only if nothing has been typed since it was filled or last saved, so a teammate's save can't overwrite what someone is typing (B10). It takes them only when they arrive, as a draft invoice's form does, never just because the form has nothing typed in it. Just after a save the page still has the settings from before it for a moment, because TanStack Query tells it of the reply on a timer, and the form, already filled from the reply, mustn't go back to them. Its checks are the backend's rules, and both sides' unit tests run the same cases from `shared/settings-cases.json`. The tax rate stays text from the box to the request, checked by its digits and never turned into a JavaScript number, so it can't be rounded on the way (B7). The opening balance goes as whole cents, read from the box as a price is, and its date is checked against `useToday`, both checked together so neither is sent without the other (B23, B24). The page and its form live in `company/`, which `App.tsx` names for the route, as it does each area's folder.
- **What other areas add to the CRM's pages:** `crm/` never imports a later area, so a later area's panel on a deal's or an organization's page (R7), or its section of the dashboard (H10), reaches the page through `App.tsx`, as search groups reach the search box. A panel is a name and a component given the record as the page has it, `RecordPanel` in `components/RecordLayout.tsx`, and a dashboard section is a name and a component, `DashboardSection` in `crm/pages/Dashboard.tsx`. `App.tsx` keeps a list of each, and each later area adds its own. Quotes adds a panel to the deal's list and the organization's, from `quotes/panels.tsx`, and Invoices adds its Invoices panel to both, after Quotes, from `invoices/panels.tsx`. Bills adds its Bills panel to the organization's list, after Invoices. The dashboard has one section, Money, which the cash flow, invoices and bills share: `MoneySection` in `App.tsx` holds its heading, then the cash flow's full-width row, `CashFlowRow` from `cashflow/CashFlowRow.tsx`, then invoices' row, `InvoicesMoney` from `invoices/MoneySection.tsx`, then bills' row, `BillsMoney` from `bills/charts/MoneySection.tsx`. Each row reads its own route and shows its own message if that read fails. The Company settings page takes the sample invoice's preview the same way, since `company/` never imports `invoices/` (B19).
- **Tables:** every section's table is `DataTable` in `components/DataTable.tsx`. A table's rows have no buttons, as Quotes' and Invoices' have, since they change only on their own page, or Edit followed by the table's own button, Delete, or both, as Bills' Mark paid and Delete. A table can give its own words for no rows and the button under them, through `empty`, as Quotes' "No quotes yet. Add the first one from an open deal." and Invoices' "No invoices yet. Start one from a won deal." with New invoice, and a filter whose usual view leaves rows out says so, through `filterNote`, as Bills under Unpaid. A column marked `hidden` is searched but not shown, such as an invoice's Bill to (V22).
- **Bills:** the bills area lives in `bills/` and follows the products area's pattern: its queries in `queries.ts`, its form and the Mark paid dialog beside them, and its pages in `pages/`. The six categories, their order, labels, color tokens and round swatch are in one place, `bills/categories.tsx`, which the table, the form, the bill page and both charts read, and paid, unpaid and overdue, worked out from `useToday`, are in `bills/status.tsx`, with the chip and the paid date's checks the form and the Mark paid dialog share. The form uses React Hook Form and Zod, as the record forms do. Its due date follows the bill date until the due date is typed in (E5), as the deal form's close date follows the stage (F8). The supplier picker is `RecordPicker` with no `onAdd`, so it offers no Add: the CRM's organization form is in `crm/forms/`, which a later area doesn't import ([Layout rules](architecture.md#layout-rules)), and a new supplier is added in Organizations first (E16). Mark paid and Mark unpaid wait for the server's reply, like any save other than the pipeline move and the follow-up tick. The Undo on "Bill marked unpaid." goes through `lib/notify.ts` like the product's Restore, so it's dropped at sign-out (U5). The Money section's charts are built with Recharts, like the CRM's, from the tooltip, `useSize` and the axes' text in `components/charts/`. Recharts stacks by series, and a day's bills aren't series, so the timeline stacks layers, each day's first bill, then its second, and colors each bar by its own bill's category, with its tooltip set to the bar pointed at. Both charts draw their segments with `StackSegment`, for the 2px gaps and the rounded tops, and stack them through its `stackScale`, which stacks a segment too small to see at 4px plus its gap, shares half the chart among a column's segments when there are too many for that, and raises the axis's top to make room. The gap takes at most half a segment, so one with money in it never vanishes. The charts' heights use numbers, close enough at any size, and every figure they show uses the exact sums. Each has a table behind it for screen readers, as the CRM's month charts have `MonthsTable`.
- **Cash flow:** the cash flow lives in `cashflow/` and imports no other area. Its row reads `GET /cash-flow`, keyed by the day as the Money section's other reads are, and draws what the reply says, adding nothing up itself (Y19). Its chart is Recharts' `ComposedChart`, built from the tooltip, `useSize` and the axes' text in `components/charts/`, as the Money section's other charts are: a bar for each month's money in and one for its money out, each with this month's expected part carried on past its actual part, the balance as two `Line`s, solid and dashed, that meet at last month's point, and the likely deals' band as an `Area` between the balance without them and the balance with them. The heights use numbers, close enough at any size, and every figure it shows uses the exact sums, as BigInt. The Likely deals switch is a checkbox with the `switch` role, kept in the row's own state, so it's off each time the dashboard opens (Y15) and needs no new package. Turning it on draws the band from the same reply, without a fresh read. The month labels of this month and the forecast are buttons, so the keyboard reaches the month dialog too, and the dialog reads `GET /cash-flow/{month}` as it opens, with N6's failed read and Try again. Its links are each record's address, such as `/invoices/7`, `/bills/3` or `/deals/12`, so it needs nothing from the areas it lists. A table behind the chart gives screen readers every month's figures, as `MonthsTable` does for the CRM's month charts.
- **Focus after a dialog:** these dialogs open without a Radix `Dialog.Trigger`, so on closing, Radix puts focus nowhere. `FormDialog` takes `onCloseFocus` for a dialog that sends it somewhere itself. Mark paid's dialog sends it back to the button that opened it, or, when a save took that button's row out of the table, to the table's search box, which `DataTable` focuses for the page through its `ref`. Buttons that change with a save, such as Mark paid becoming Mark unpaid, keep their place in the row and the header, so focus stays on them.
- **The top bar's sections:** `App.tsx` gives the shell its sections, each an address, a label and an icon, so `components/Shell.tsx` names no area's pages, and a later area adds its section beside its routes. The shell hides each icon below 1536px wide and narrows the links' padding, with Tailwind's `max-[1536px]` and `min-[1536px]` (N1).
- **Files to download:** `fetchFile()` in `lib/api.ts` fetches a file the backend sends, with the token in its header as for any request, and gives it as a `Blob`, with `api()`'s errors. `download()` is built on it, and saves the file under the name given, letting go of it once the click has handed it to the browser. A plain link can't, because the token never travels in a cookie. Quotes' and invoices' PDFs download this way (Q30, V24). The logo is read with `fetchFile()` too, since an `<img>` can't send the token, and shown as a data address, from `lib/files.ts`, which leaves nothing to let go of.
- **Fields in a list:** `lib/saveErrors.ts` puts a save's error on a field in a list, such as `lines.2.quantity`, beside that field, and an error about the form as a whole, under `form`, at the form's top as React Hook Form's `root.form`. An error on a field the form doesn't have, or on a line it doesn't have, shows as a message, so it's never lost. A quote's and a draft invoice's line keep their quantity and price as typed under the backend's names, `quantity` and `unit_price_cents`, as the payment form keeps `amount_cents`, so the backend's messages land without any renaming.
- **Sums on quotes and invoices:** `company/tax.ts` works out a line's amount, the subtotal, the tax and the total as `company/tax.py` does (B16), reads the rate from the backend's text by its digits, and reads a typed quantity (B17). It multiplies the subtotal by the rate through BigInt, so the cent is right past a subtotal of $900 million. Both sides run the cases in `shared/totals-cases.json`. The quote page uses it for the form and the preview as you type (Q15), and a draft invoice's page for the figures it shows as you type, before they're saved (V7).
- **Quotes:** a draft's form uses React Hook Form and Zod, as the record forms do, with its lines as a field array, filled from `GET /quotes/{id}`, or from `GET /quotes/new/{deal_id}` for a new draft, and saved through `useWrite` in `lib/records.ts`. It takes a teammate's newer save only if nothing has been typed since it was filled or last saved, as the Company settings form does (B10). The preview, `quotes/QuoteDocument.tsx`, draws from the form's values as they're typed, with the company's details, Prepared for and the tax from the reply, and the sums from `company/tax.ts`, so it updates with each keystroke without asking the backend. A saved quote that isn't a draft draws from the reply alone. Mark as sent and Download PDF on a draft with changes save them first, through the same save. Whether a sent quote has expired is worked out with `useToday`, so a page left open past midnight shows it. The Quotes table's figures are worked out in the browser from the list, as the board's are. The quotes area imports only `crm/queries.ts`, `crm/deals.ts`, `products/queries.ts` and `company/`, and reaches the deal's and organization's pages through `App.tsx`.
- **Invoice previews:** the browser draws the preview itself, so it follows every keystroke without asking the backend (V19), and the backend makes the PDF. They agree because both draw from one description of the three designs, `shared/invoice-designs.json`, which holds every size, place, font and color on the page, and both lay the page out the same way: `invoices/layout.ts` in the browser and `invoices/layout.py` on the backend. Both measure text by the fonts' own character widths, kept in `shared/invoice-fonts.json`, made from the font files the PDF carries, rather than by what the browser measures, so a line breaks after the same word and a page turns after the same line on both. Kerning is off on both. The same table says which characters the fonts have, so the page and the backend refuse the same ones in a draft (V9). Both unit suites run the cases in `shared/invoice-layout-cases.json`, such as a long description, a long Bill to and an invoice of 100 lines. The preview draws the page as SVG, in the fonts the app already bundles, scaled to its column.
- **A draft invoice's form:** React Hook Form and Zod, as the record forms use, with the lines as a field array. Leaving with changes not yet saved asks first, through React Router's blocker, and the browser's own question covers a reload or a closed tab (V8). After a save or an issue, everything is read again, as after any write.
- **A draft invoice and a newer reply:** its form takes a newer reply, such as a teammate's save, only if nothing has been typed since it was filled, as the settings do (B10), and only when a new reply arrives: refilling it from the same one would remount every line's boxes and lose the focus. Each line in the form has a key of its own, never sent, so when something was typed while a save was on its way, the save's reply can still give each new line it saved its id, leaving what was typed alone (V8).
- **Invoices and today:** the backend says what each invoice shows as, from its own today (V3). Pages that show invoices, and the Money section, read them again when `useToday` sees the day change, so Overdue appears the morning it's due. Each read is keyed by the day, and while the same invoice or list is read for the new day, the last day's reply stays on screen, so nothing leaves the page meanwhile and a draft keeps what was typed. Another invoice's or list's reply never stands in.
- **Company settings' Documents panel:** the accent color is checked as it's typed, by the formula the backend uses (B20). A chosen logo is checked for its size and ending, shown in the preview from the file at once, and sent with Save settings as base64. Remove logo sends null.
- **Theme:** every color is a CSS variable in the `@theme` block of `styles.css`, and dark mode gives the same variables their dark values under `[data-mode="dark"]` on `<html>`. Components name tokens, never a mode or a color value, so nothing but `styles.css` knows dark mode exists. The paper tokens, which the quote document uses, have the same value in both modes, because the document shows the paper ([Quote document](quotes.md#quote-document)). The charts already take `var(--color-...)` values, so they follow along. The theme, `light`, `dark` or `system`, is saved in `localStorage` as `accountable-mode`, the key light and dark were saved under before System existed, so an earlier choice carries over. A short script at the top of `index.html` reads it, works out the mode, asking the browser's `prefers-color-scheme` for System, and sets `data-mode` and the page's `color-scheme` before anything draws. Vite's dev server delivers the styles through JavaScript, so for a moment there are none, and `color-scheme: dark` makes Chrome paint that moment dark rather than white. `color-scheme` also makes the browser's own date pickers, select lists and scrollbars follow the mode. With System chosen, `lib/theme.ts` listens for the device's setting to change and switches the mode at once. If the saved choice can't be read, the app opens in Light. Sonner's own color variables are set from the tokens in `styles.css`, in both modes.

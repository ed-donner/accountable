# Spec: Frontend

Part of the [spec](../spec.md), which has the summary, the terms, the quality rules and the index of every area file.

## Frontend

- **Data:** TanStack Query holds all server data, and it refetches when the window regains focus, which is also when teammates' changes show up. After any write, invalidate everything. With a small team and this little data, that's simple and hard to get wrong. Queries and saves use `networkMode: 'always'`, because the local copy runs with no internet, and the browser reporting it's offline would otherwise pause them (C2).
- **Signing in:** `lib/session.ts` holds the session and is the one place that signs in and out, for both copies. In the shared app it uses Supabase's JavaScript client with the publishable key, which keeps the session in this browser's storage and renews the token before it expires. In the local copy, the sign-in screen asks the backend's local sign-in route for a token, through `lib/api.ts`, and `session.ts` keeps it in storage, where each request reads it. If storage is off or full, `session.ts` keeps the token itself, so the person stays signed in until the page is reloaded. `session.ts` imports nothing from `api.ts`, so the two load in one order. The frontend knows which copy it's in from whether the Supabase URL and key were built in (W2): `npm start` and Render build them in, and `npm run dev` never passes them to Vite (C9). `lib/api.ts` adds the token to every request. A 401 shows the sign-in screen with U6's message, but only if the session the request went out in is still going: each sign-in begins a session with a new id, so a refusal arriving after someone has signed out and in again leaves the new session alone. `SignedIn` gives each session its own query cache, made when the session begins and dropped when it ends, and the sign-in screen has one too. So nothing from one session shows in the next, even a reply or a pipeline move that finishes after it ended, which lands in the old cache (U5).
- **Today:** the page can stay open for days, so anything on screen that depends on the date uses `useToday`, which checks the clock every minute and whenever the window is used again. The dashboard reads its figures again when the day changes. The browser's today is the device's, and the team shares one time zone, so it matches the backend's.
- **Instant updates:** only the pipeline move and the follow-up tick update the screen before the server replies, and both roll back on failure. Moves share one mutation scope and ticks another, so each kind is sent one at a time and in order. Reads they would affect are cancelled first, so an older reply can't overwrite them. The board shows what the server has confirmed plus the moves still on their way, so a failed move or tick puts back only its own change.
- **Money:** `lib/money.ts` shows a deal's whole dollars as `$48,000` and a product's cents as `$49.50` or `$1,250.00`, always with two figures after the point (G3). It also turns a typed price into cents (G4) by reading the dollars and the cents as two whole numbers, never by multiplying a decimal by 100, which gives 28.999999999999996 for 0.29. A price that can't be read, or has a third figure after the point, is refused rather than rounded. The frontend and the backend only ever pass prices to each other as whole cents.
- **Board figures:** worked out in the browser from the deals list, so they change as a card lands. They use the same formula as the backend, with a unit test on each side using the same cases.
- **Dragging:** a 6px move starts a drag, so a click still opens the deal. Keyboard dragging comes from dnd-kit's keyboard sensor, set to pick up and drop on Space only, because by default Enter would pick up the card instead of opening the deal. Cards are memoized to stay smooth at 500 deals. Columns aren't virtualized, because that conflicts with dropping a card anywhere. Each column is a droppable, and the board has one draggable that's pointed at a card as it's picked up. While a card is dragged, the others slide apart around a faint slot showing where it will land, and the gap closes behind it. `@dnd-kit/sortable` isn't used: its per-card hooks re-render every card each time a drag crosses a card, which took 241ms at 500 deals. The longest task on this board is about 70ms to 180ms, slowest on the first drags after loading.
- **Dialogs inside dialogs:** a form in a second dialog, such as adding an organization from a picker, stops its submit event from going further. React passes events up through portals, so it would otherwise submit the form underneath too.
- **Search:** the search box waits for a 150ms pause in typing, then asks `GET /search` through TanStack Query, keyed by the text, so a newer search's reply always wins and going back to an earlier text shows its results at once. The box lives in `components/Search.tsx` and knows nothing about any area's records. Each area gives it its groups, each with its heading, the address a result opens, and how a result's detail shows, such as a deal's stage chip or a product's price. `App.tsx` hands the box the groups in order, CRM first, and hands the box to the shell. The box's label for screen readers and its message for no matches are made from the groups' names, so a later area's group joins them by itself.
- **Theme:** every color is a CSS variable in the `@theme` block of `styles.css`, and dark mode gives the same variables their dark values under `[data-mode="dark"]` on `<html>`. Components name tokens, never a mode or a color value, so nothing but `styles.css` knows dark mode exists. The charts already take `var(--color-...)` values, so they follow along. The theme, `light`, `dark` or `system`, is saved in `localStorage` as `accountable-mode`, the key light and dark were saved under before System existed, so an earlier choice carries over. A short script at the top of `index.html` reads it, works out the mode, asking the browser's `prefers-color-scheme` for System, and sets `data-mode` and the page's `color-scheme` before anything draws. Vite's dev server delivers the styles through JavaScript, so for a moment there are none, and `color-scheme: dark` makes Chrome paint that moment dark rather than white. `color-scheme` also makes the browser's own date pickers, select lists and scrollbars follow the mode. With System chosen, `lib/theme.ts` listens for the device's setting to change and switches the mode at once. If the saved choice can't be read, the app opens in Light. Sonner's own color variables are set from the tokens in `styles.css`, in both modes.

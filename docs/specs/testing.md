# Spec: Testing

Part of the [spec](../spec.md), which has the summary, the terms, the quality rules and the index of every area file.

## Testing

`npm test` runs the type checks, tsc on the frontend, because Vite doesn't check types, and ty on the backend, then all three layers, and uses databases of its own. `scripts/checks.mjs` picks the database path once and passes it down. Pytest and Playwright refuse to start without it, or with a path inside `data/`, so a test can never wipe real data. Pytest also refuses if any of the three Supabase settings is set, so a by-hand `uv run pytest` can't reach the team's data either.

Every test runs as the local copy, on SQLite. The checks never read `.env`, and pass down an environment without the three Supabase settings (C9), so no test can reach Supabase, whether the settings are in `.env` or not, and CI needs no secrets. Where a test needs Supabase, such as the shared app's token check, it stands in for it.

**Speed:** every unit test, backend and frontend, old and new, runs in under a second on the developer's computer, because CI runs on a much slower machine. The summary at the end of `npm test` names any unit test that took a second or more. If another test run on the computer was busy while the unit tests ran, a line under that list says so, because the other run can make them slow.

**Colors in one place:** `frontend/src/colors.test.ts` fails if any file in `frontend/src` other than `styles.css` names a color value, such as `#fff` or `rgba(...)`, so every color comes from a token and has a dark value. It also fails if the dark block sets a token that `@theme` doesn't have, so a misspelled one can't go unnoticed.

**Unit coverage:** `npm test` fails if the unit tests cover less than 80% of the app code. For `frontend/src` that's lines, statements, functions and branches, leaving out the tests, `test-setup.ts` and `test-utils.tsx`. For `backend/accountable` it's lines and branches together. The end-to-end tests don't count towards it.

**Code checks:** `npm run check` runs these alongside the type checks and unit tests, then the browser tests, and fails if any of them fail. Warnings fail it too.

- Prettier on the code, settings and styles, 120 characters wide, as the code was already written. It leaves out Markdown, `docs/`, `course/`, `package-lock.json`, `.claude/` and `.mcp.json`, because their authors or their tools write them.
- ESLint on all the JavaScript and TypeScript, with the recommended rules from ESLint, `typescript-eslint`, React Hooks and `jsx-a11y`, the last two on `frontend/src` only. In `frontend/src`, it refuses `toast` from Sonner outside `lib/notify.ts` and the tests, so every message stays with its session (U5). It leaves out `.claude/worktrees/`, where Claude Code keeps its worktrees: they're other checkouts of the repo, which git ignores and which run their own checks. Prettier, ruff, ty and gitleaks already leave them out, by following `.gitignore`.
- ruff format and ruff check on the backend, with ruff's default rules, 120 characters wide. Ruff also formats Python inside Markdown, so Markdown is left out.
- A complexity of at most 15 per function, through ESLint's `complexity` rule and ruff's C901.
- gitleaks on every commit and on the files as they are now, with gitleaks' own rules. `.gitleaks.toml` allows only `.env`, which git ignores. gitleaks is a program of its own, not an npm or Python package, so it has to be installed, and the check says how if it's missing. It names the file and line of anything it finds, with the secret itself hidden.

`npm run check:quick -- --failures-only` shows only the output of the checks that fail, then the summary.

**Hooks:**

- Before each commit, lefthook formats the staged files with Prettier and ruff and adds the changes to the commit. Then it runs ESLint and ruff check on those files, tsc and ty on the whole project, and gitleaks on what's staged. It leaves out the tests, so a commit takes a few seconds. `npm install` sets it up. If a staged file also has unstaged changes on the lines formatting touches, lefthook stops the commit and leaves both as they were, rather than mix them.
- When the coding agent finishes a turn, a hook in `.claude/settings.json` runs `npm run check:quick -- --failures-only` and sends what failed back to the agent to fix. It does that once a turn: the next time the agent stops, the hook lets it, so it can't loop. The check takes about 30 seconds, so every turn ends with that wait. It's a test run like any other, so while two other runs are going it waits for a turn, and for any speed tests that come first: several minutes, behind two runs of `npm run check`. The hook has 30 minutes, set in `.claude/settings.json`, rather than Claude Code's default of 10, so a wait doesn't cut it off.
- Another hook stops the agent's file tools from changing any file called `.env`, and stops any shell command that names `.env`, because a command can change a file in too many ways to tell a read from a write. It guards against mistakes. It isn't a sandbox: a command could still reach the file without naming it. If the hook itself fails, the edit or command is stopped too.
- A third stops a shell command that runs `python`, `python3`, a version such as `python3.12`, `pip` or `pip3` itself, where a command starts, and says to use `uv run` or `uv add`. It skips quoted text and the body of a heredoc, so `grep python` or a file written with `cat <<'EOF'` still runs. Agents ran a bare `python3` on several branches, though the owner asks for `uv run`. Like the others, it guards against mistakes and isn't a sandbox.

**Subagents:** the coding agent has two, in `.claude/agents/`. Claude Code loads that folder when a session starts. Each one ends with a report in a set layout, and the hook in its file runs only once the project folder is trusted in Claude Code. If the hook itself fails, the tool call is stopped.

- **reviewer** reviews a branch, a commit or a range against `docs/REVIEW.md`, reading the spec, `AGENTS.md`, `docs/STANDARDS.md` and the branch's `plan.md`, and reports Important findings and at most five nits. By default it reviews the current branch against `main` as it stands in the working tree, including work not yet committed. It runs on Sonnet, so that a different model from the session's checks the work. It has Read, Grep, Glob and Bash. Claude Code can't limit Bash to some commands through the tool list, so a hook lets it run only commands that read: `git blame`, `cat-file`, `describe`, `diff`, `grep`, `log`, `ls-files`, `ls-tree`, `merge-base`, `rev-list`, `rev-parse`, `shortlog`, `show` and `status`, `git branch` to list branches, and `cat`, `cd`, `cut`, `diff`, `echo`, `grep`, `head`, `ls`, `pwd`, `rg`, `sort`, `tail`, `tr` and `wc`, and `sed` only as `sed -n` printing one range of lines, such as `sed -n 40,100p`, because sed's other commands and flags can write a file or run a program. They can be joined with `|`, `&&` or `;`, and send output to `/dev/null`. It stops redirects into a file, `$( )`, backticks, subshells, and the flags that let those commands write a file or run another program, such as `git diff --output` and `rg --pre`. Like the `.env` hook, it guards against mistakes and isn't a sandbox.
- **ui-check** opens the local copy that `npm run dev` starts, at `http://localhost:5173`, with the Playwright MCP server, and checks each page against the brand skill, which its file loads, and the spec. It checks the sign-in screen first, then signs in by clicking one of the made-up teammates, so it needs no password and never touches Supabase. The pages are the routes in `frontend/src/App.tsx`, with the first record of each kind and an unknown address, plus the open menu. By default it checks every page at 1440 by 900 in light mode and then dark mode, switching with the menu, reading computed styles to confirm fonts and colors, and the console and network for Q2 and C2. It reports what's broken, what's off-brand and up to five nits. It runs on Sonnet. It has Read, Grep, Glob and the browser tools that look rather than enter data: it can open pages, dialogs and the menu, but can't type, drag or upload, and never saves, deletes or ticks anything, because the running app holds someone's records. Without typing it can't see search results, so those are left to the end-to-end tests. A hook stops any Playwright tool from saving a file outside `.playwright-mcp/`, which git ignores, because a bare file name would land in the project folder.

**CI:** `.github/workflows/ci.yml` runs on every push, to any branch, on GitHub's Ubuntu runner. It installs gitleaks and runs it on every commit first, so a leaked secret fails the run straight away. Then it installs Node 26 and the latest uv, and runs `npm run check:quick`. It leaves out the end-to-end and speed tests, which took most of each 15-minute run, so they run only in `npm run check` on the developer's computer. It uses no secrets, and its token can only read the repo.

**End to end (Playwright Test)**, with the installed Chrome, not in CI:

- The tests run the local copy. Each test starts signed in as a made-up teammate, through the local sign-in route, apart from the sign-in tests, which use the screen. The shared app's sign-in to Supabase is covered by the unit tests and checked by hand, below.
- The tests run on several workers, chosen from the machine's cores and memory, and `ACCOUNTABLE_TEST_WORKERS` sets the number by hand. Each worker has its own servers and its own temporary database, with `reuseExistingServer` off. If they reused a server, they could attach to a running copy of the app and change real data. Tests that stop and restart the app start their own copy, on two more ports of the worker's own.
- The tests' Vite servers, copies included, watch no files: the run sets `ACCOUNTABLE_VITE_WATCH=off`. So a file saved during a run, by the person, an agent or a teammate, can't reload a page mid-test or move its script to a new address. Each file is served as it was when the run first asked for it. `npm run dev` still reloads on a save. `scripts/vite-watch.test.mjs` serves a throwaway folder with the app's Vite config, beside a server that does watch. It changes the file in both until the watching server serves the change, then checks the other still serves the file as it was.
- Several runs can share one computer, such as `npm run check` in three worktrees, with nothing to set. Each run of `npm test`, `npm run check`, `npm run check:quick` or `npm run e2e` takes a slot, by listening on the slot's port, from 20001 to 20016, and the slot holds a block of ports for that run's servers, from 20017 up, four for each worker. A slot where another program has one of the run's ports is passed over. The operating system frees the slot's port when the run ends, even if it crashes, so there's nothing to clean up. The ports stay clear of `npm run dev`'s and `npm start`'s, of the ports from 5200 to 8963 that the tests used before slots, so that an older branch's run can't clash with a newer one, and of the ports the system hands out for connections. At most 16 runs can be on the computer at once, going or waiting, and the 17th stops with a message.
- No more than two runs go at once, because three at once overload a 10-core Mac and their tests time out. A run waits for a turn before its checks, and holds it through its end-to-end tests, by listening on the turn's port, 24113 or 24114, which come after every worker's ports. The others queue in the order they started waiting, which each says on its slot's port, and a run tries for a turn only when fewer runs are ahead of it than turns are free, so they go first come, first served. The port settles it if two try for one turn at the same moment. While a run waits it prints a line saying why, with how many runs are ahead of it, once the reason has lasted two looks a quarter of a second apart, so that it doesn't report runs that are already taking the free turns. It prints again when the reason changes, then how long it waited once its turn comes. `TURNS` in `scripts/test-plan.mjs` sets how many go at once. Another program on a turn's port stops a run that needs it with a message, as on the speed tests' port.
- Runs share the machine. When a run reaches its end-to-end tests, it divides its workers by the number of runs that are busy with their checks or end-to-end tests, its own included, so two runs at once take 3 workers each on 10 cores rather than 6. `ACCOUNTABLE_TEST_WORKERS` still wins.
- Every test fails on any console error it didn't name in advance, and on any request to an address outside the computer. The second check proves the offline requirement. Tests that expect a failed request, such as the 404 behind N4, name the exact message.
- Drags use `page.mouse` with several small moves, because dnd-kit needs to see the pointer travel.
- A stress run fills a test database to the limits in Q1 and checks the timings, taking the median of five readings. It runs last and alone, because timings need a quiet machine. Alone means on the whole computer: one run at a time holds the speed tests' turn, by listening on port 20000, and starts them only once no other run is busy with its checks or end-to-end tests. Each run says what it's doing to anyone who connects to its slot's port: waiting for a turn, busy, or at its speed tests. When its end-to-end tests end, a run says it's at its speed tests, then gives back its turn. A run waiting for a turn also waits while any run is at its speed tests, waiting for them or running them, so the speed tests of every run that has finished its end-to-end tests come before the next run's checks, and the speed tests' turn always comes. A run waiting for a turn isn't busy, so the speed tests don't wait for it. Both waits print a line saying what they're waiting for.
- `scripts/test-plan.test.mjs` checks that no port is shared between workers, runs or turns, even at 16 runs of 64 workers, and that the workers are shared out between runs. `scripts/test-runs.test.mjs` checks, on ports the system picks so it can't disturb a real run, that two runs get different slots, that a slot with a taken port is passed over, that no more than two runs go at once, that a run never takes a turn another run holds, that the turns go in the order the runs started waiting whatever their slots, that a waiting run says why only once the reason lasts, that the speed tests wait for a busy run but not for a waiting one, that a run waits for a turn while another run holds the speed tests' turn or is waiting for it, that only one run has the speed tests' turn at a time, and that another program on the turns' ports or the speed tests' port stops a run with a message.
- Tests reach the app at 127.0.0.1, so a slow lookup of the name `localhost` can't stall them, and Chrome runs with `--disable-gpu`, because browsers compiling shaders side by side can hang on macOS.
- Each run leaves an HTML report, with a screenshot of each failure and how long each step took, in `playwright-report/main` and `playwright-report/speed`. The next run replaces it.
- `npm run e2e` runs only the end-to-end tests it's given, with Playwright's own arguments, such as `npm run e2e -- e2e/settings.spec.ts -g "a save"`. It sets up the run as `npm test` does: a slot, a turn, a temporary database and its share of the workers. It ends with the same summary, fails if no test matches, and leaves its report in `playwright-report/main`. It doesn't run the speed tests.

**By hand:** tests can't settle everything. The app is also used in Chrome at 1440 by 900 and 1280 by 720 the way a salesperson would, including with an emptied database, after a restart and with the network off, and each screen is compared with the design reference, in light mode and dark mode. The project owner checks that someone with no instructions can answer the five questions from the dashboard (H9), and has the final say, including on how it looks. Each of the three invoice designs is downloaded as a PDF, with a logo and a dark and a light accepted accent color, opened beside its preview to check they look alike, and printed once in black and white to check it still reads. Passing tests is necessary, but it isn't enough.

The shared app is checked by hand too, because no test touches Supabase. The project owner runs `npm start` against an empty Supabase database, which proves that every migration runs from empty on Postgres and that the startup check for row-level security passes. Then they sign in as their Supabase user, and go through the change's success criteria, such as a wrong password, signing out, who added each record, search, the theme, the company settings and an invoice from draft to paid, with its PDF and a logo. For the company settings, that includes running the clearing steps in `docs/STATUS.md`, which should leave no records and the Company settings page asking for a company name, with no one shown as having changed the settings. Once `npm start` has built the tables, the coding agent uses the Supabase MCP server to confirm that row-level security is on for every table and to run Supabase's security advisors, reporting only. After the first deploy, the same checks run on the `onrender.com` address.
